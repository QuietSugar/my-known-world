# Incremental source sync (first slice)

This slice introduces a conservative domain reconciliation operation and a read-only preview endpoint. It is a protocol foundation, not yet a configured importer or persistent apply endpoint.

`POST /api/operations/preview` accepts `{mutation:{kind,node?,relation?,id?}}` for `createNode`, `updateNode`, `addRelation`, `deleteRelation`, and `deleteNode`; it returns a graph `expectedRevision`, payload `planHash`, and entity-ID delta without changing state. Authenticated `POST /api/operations/apply` must return the same mutation plus both preview tokens; it rejects stale revisions or changed payloads and atomically records the operation for undo. The Web object-create/edit/relation controls use this flow. `GET /api/operations` lists recent manual graph mutations; authenticated `POST /api/operations/{id}/undo` restores a prior state only when the current graph fingerprint still exactly matches that operation's post-state. This prevents stale rollback from overwriting later edits; each undo is itself recorded in entity history. Undo snapshots are stored in the private PostgreSQL database, not returned by the API; only the newest 50 manual operations retain rollback payloads, while older operation summaries remain audit-only. Applied sync batches also enter this operation stack. Undo restores the graph, previous source hash/parser state and identity mappings atomically; the sync run remains in history marked `undone`. Only the last 50 operations retain rollback snapshots.

Authenticated maintenance routes now include `PUT /api/nodes/{id}` (ID, type, and source ownership remain immutable), `POST /api/relations`, and `DELETE /api/relations/{id}`. Relation insertion validates endpoint types; deletion is rejected if it would disconnect any published object from Self. All operations are transactional and append change-history events. The Web detail drawer edits node names and typed details (strict JSON) and adds/removes relations; the create dialog supports explicit types, JSON details, and a required Self relationship. These writes are authenticated but do not yet offer a complete before/after review or undo.

`GET /api/sync/policies` lists configured source allow-lists. Authenticated `POST /api/sync/policies` creates or replaces one `{source,priority,allowedNodeTypes,allowedPredicates,allowedFieldPaths}` policy. If configured, both preview and apply reject any out-of-scope entity/field; rejection is atomic. Empty allow-lists allow no records of that category. Priority is metadata only and never auto-selects conflicting claims. Unconfigured sources retain legacy behavior.

## Generic machine-inventory CSV adapter

`cmd/myknownworld-csv-import -input inventory.csv -source private-inventory` converts a CSV into the same `SourceBatch` JSON accepted by the sync CLI/API. Required headers: `id,name,hostname`; optional recognized headers: `os,status,ip`. Unknown columns (including passwords, notes, and free-text descriptions) are ignored, never copied. Required fields, duplicate IDs, and invalid IP rows are reported under `exclusions` with line number and reason; only valid rows become Machine nodes. The adapter requires an explicit source and emits JSON only; it does not connect to a database. Pipe/save its output privately, inspect the batch and exclusions, then use `myknownworld-sync` preview and the explicit apply confirmation. This is a generic documented format, not a connector to any real inventory product.

## Preview

`POST /api/sync/preview` accepts one JSON `graph.SourceBatch` (maximum 2 MiB):

```json
{
  "source": "synthetic-example",
  "nodes": [
    {"id":"example-machine","type":"Machine","name":"Example machine","modelVersion":1}
  ],
  "relations": []
}
```

The endpoint returns arrays for added/updated/missing nodes and relations, and conflicts. It does not mutate the graph. Without a mapping, IDs act as stable graph identity keys. For a known source-side rename, include an explicit `identityMappings` entry such as `{"sourceId":"new-source-key","nodeId":"existing-stable-graph-id"}` and use the new source key as the incoming node ID and relation endpoint. The rename then updates the canonical graph node rather than creating a duplicate. The PostgreSQL store path persists mappings, reuses them on later applies, and resolves them for the HTTP preview when the app is connected to PostgreSQL. In in-memory mode the caller supplies mappings in the preview request. Previews include a deterministic SHA-256 over normalized batch content when `sourceHash` is omitted, and carry a parser version when supplied.

## Apply semantics (domain API)

`(*graph.Graph).ApplySync(batch)` returns a new graph or an error; it never partially mutates its receiver. The caller must persist the returned graph as one atomic transaction. Same-source records can be updated, while another source cannot silently take over an existing ID or alter a relation's endpoints. Records missing from a complete batch are retained and marked `stale`, not deleted. New unconnected nodes receive only a weak `Self — knowsAbout → node` link, never inferred ownership or maintenance. Invalid endpoints or a result that disconnects existing nodes reject the complete apply.

A batch is a complete observation for its named source. Do not submit partial pages as complete batches. PostgreSQL `Store.ApplySync` performs the graph replacement and source hash/parser-version/identity-mapping metadata write in one serializable transaction. `GET /api/provisionals` lists pending candidates. Authenticated `POST /api/provisionals/{id}/review` with `{"targetType":"Machine"}` classifies a candidate, while `POST /api/provisionals/{id}/reject` retains it with rejected status. Classification preserves ID and provenance and fails if existing relation endpoints would become invalid. `POST /api/sync/apply` applies an entire batch atomically. The Web UI's Batch sync view accepts a pasted JSON batch, shows the preview delta, asks for explicit confirmation, and uses the session-only write token for apply. `GET /api/sync/sources` lists the latest hash/parser version for each applied source, and `GET /api/sync/sources/{source}/history` returns up to 100 recent successful run reports (IDs and change categories, not payload bodies). `GET /api/entities/{node|relation|assertion}/{id}/history` returns the latest 100 append-only entity change events with safe modeled snapshots; these timestamps are system-recorded times, not inferred real-world validity periods. `GET /api/nodes/{id}/assertions` returns safe assertion metadata and current `resolved`/`selected` status, omitting the value hash. `GET /api/nodes/{id}/resolutions` lists up to 100 field decisions; authenticated `POST /api/assertions/resolve` appends a decision containing `nodeId`, `fieldPath`, one or more same-field `selectedAssertionIds`, and a safe `rationaleReference`. Resolutions never rewrite or remove assertions and are not currently treated as ground-truth truth values by other APIs. `DELETE /api/nodes/{id}` is an explicit authenticated deletion; Self is protected, attached relations/assertions are removed, and deletion is rejected if any remaining node would become disconnected. All HTTP write routes require `Authorization: Bearer <token>` and are disabled unless `MYKNOWNWORLD_WRITE_TOKEN` is configured with at least 32 bytes; use a stable random secret and keep it private. Compose binds the app to localhost by default. The browser review view asks for the token and keeps it in session storage only. Do not put private personal data, document bodies, credentials, or secrets in public fixtures or requests to public demos.
